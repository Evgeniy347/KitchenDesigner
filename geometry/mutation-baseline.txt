# Базовый уровень mutation score — ЕДИНСТВЕННОЕ место, где живёт число ворот.
# docs/HARDENING-PLAN.md -> C1.
#
# Читают двое, и это важно: tools/mutation-test.ps1 передаёт порог Стрейкеру
# ключом --break-at (он и роняет прогон), а MutationBaselineTests проверяет
# сам файл — что порог не отстал от замера настолько, что перестал стрелять,
# что скрипт всё ещё его читает и что ни один проект быстрого пути не остался
# без строки. Число в скрипте было бы декоративным: его никто не сверяет.
#
# Порогов ДВА, по одному на сборку, и слить их в один нельзя:
#   * Stryker мутирует ОДИН проект за прогон (--project) и по своему тестовому
#     проекту; общий процент пришлось бы считать руками, и его никто не проверит;
#   * состав чистого слоя сейчас растёт (перенос ElementData в Core/Pure), а
#     общий процент поехал бы от каждого ПЕРЕНОСА файла, ничего не говоря о
#     качестве тестов — ворота стали бы то ложно красными, то молча опущенными;
#   * общий процент прячет регресс: провал в ядре (1039 мутантов) закрывается
#     ростом меньшего слоя. Храповик существует ровно против такого маскирования;
#   * упавший процент должен называть СБОРКУ, иначе первый шаг после красноты —
#     выяснять, где именно потеряно покрытие.
#
# Формат строки: <проект> <замер> <порог>
#   проект — каталог под geometry/
#   замер  — что показал Stryker на коммите из строки #baseline ниже
#   порог  — целое; ниже него прогон падает. Порог = замер, округлённый ВНИЗ:
#            запас в один процент — это ровно тот запас, в который прячется
#            потерянная проверка.
#
# Подняли счёт — поднимите порог тем же коммитом, иначе храповик отдаст назад.
#
# Замеры сняты на РАЗНЫХ коммитах, и это не небрежность, а та самая причина,
# по которой порогов два: состав чистого слоя ехал прямо во время работы.
