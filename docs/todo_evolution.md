## Часть 2 — Сайдбар

Жалоба: *«сайдбар слишком разрастается, может его переделать, может расположить внизу (как
в The Sims 2), и я хочу чтобы были картинки элементов с надписями»*.

### 2.1 Почему он разрастается: структура или подача

**Обе причины, и структурная — первичная.**

Структурная. `SidebarCatalog` — плоский список рецептов спавна. В нём смешаны два разных
уровня:

| Уровень | Примеры | Сколько позиций |
|---|---|---|
| **Тип** элемента (свой класс, свой меш, своя панель) | Полка, Фасад, Ящик, Стол, Стул, Мойка, Труба, Унитаз… | ~24 |
| **Вариант/пресет** того же типа (отличается параметром) | Ящик GTV / Movento (`drawerSystem`), Варочная общая / Bosch (`applianceModel`), 6 фитингов (`PipeNodeKind`), Щитовой / Сборный фасад (`AssembledFill`) | +14 |

Каждый вариант сегодня — отдельная кнопка первого уровня. Сантехника одна принесла 12
позиций, из которых 6 — фитинги одной трубы. **Вентиляция (3.5) принесёт ещё 6–8 фитингов
воздуховода тем же способом**, фундамент, забор, кровля, три слоя стены — ещё ~10. Рост
линейный по типам И по вариантам, и никакая раскладка это не спасёт.

Подача. Всё раскрыто по умолчанию, одна колонка 236 px, строка ~40 px после D8, без
картинок, без поиска. На 638 px высоты — три экрана.

Что делать со структурой (**до** любой раскладки, иначе плитки унаследуют те же 38):

| Что | Зачем | На что ложится | Цена |
|---|---|---|---|
| Разделить `Item` на **тип** (плитка) и **пресет** (вариант внутри плитки): фитинги → одна плитка «Фитинг» с рядом из 6 маленьких иконок; ящик → одна плитка с переключателем GTV/Movento; варочная → одна плитка, модель — пресет | 38 → ~24 плиток первого уровня. Фитинги воздуховода — тоже одна плитка. | `SidebarCatalog.Item` уже несёт все поля пресета (`drawerSystem`, `applianceModel`, `dims`); `SidebarSpawnRouter.Route` не меняется — получает тот же `Item` | 1–2 дня; `SidebarCatalogTests` переписать под «тип + пресеты» |
| Каталог → **данные**: таблица `(kind, title, group, dims, preset...)` в одном месте, а не 20 фабричных методов; группы — тоже данные, с иконкой | Позицию добавляет один список, а не пять файлов. Часть 3 добавляет группы «Участок», «Конструкции», «Кровля», «Вентиляция» строками, а не классами. | `SidebarCatalog.Build()` остаётся единственной дверью; `SidebarSpawnRouterTests` (паритет с MCP) продолжают жить | 1 день |
| Пресет «последний использованный» на плитке | Тот, кто ставит только Movento, не выбирает его каждый раз | `KitchenSettingsData` (сохраняется в проект) | 0,5 дня |

### 2.2 Нижняя лента «как в The Sims 2»

Что это на самом деле: горизонтальная полоса внизу экрана; слева столбик иконок-категорий
(≈8), под ним подкатегории; справа сетка миниатюр 2 ряда × 8–10 плиток с постраничной
прокруткой стрелками; поиска нет; клавиатуры нет; при наведении — карточка с ценой.

Как это ложится на этот продукт, **на базовом экране 1366×768**:

| Критерий | Нижняя лента | Комментарий |
|---|---|---|
| Категории | 7 (скоро 11) групп → иконки слева. Ложится. | `SidebarCatalog.Group` уже есть. |
| Вложенность | Sims: категория → подкатегория → страницы. Здесь глубина 2 (группа → тип → пресет) — ложится, пресеты внутри плитки. | |
| Сколько помещается | Лента 200 px (2 ряда плиток 88 + подписи), ширина 1366 − 200 (рейка) = 1 166 px → **2 × 11 = 22 плитки**. | Больше, чем в доке, — единственный плюс. |
| 100+ типов | Страницы. Худший паттерн поиска: не видно, что существует. | **Минус.** |
| Поиск / клавиатура | Поле на ленту прикрутить можно; навигация стрелками по сетке внизу экрана неестественна. | Минус. |
| Что закрывает | **Низ экрана — это пол сцены.** Спавн ставит элемент в точку земли перед камерой (`ElementSpawner._groundPointInFrontOfCamera`), при типичном ракурсе это нижняя половина кадра. | **Главный минус.** |

найти один из 40–100 типов и поставить его туда, куда смотришь). Но в идее три правильные
вещи, которые надо взять: **плитки с картинками и подписями, иконки категорий вместо
текста, один экран без прокрутки для одной категории.** Их реализует вариант A ниже.

### 2.3 Картинки элементов с подписями — откуда брать

Мебель процедурная, вид зависит от размеров и декора. Значит, картинка — не ассет, а
**производная от кода**, и её надо рендерить тем же кодом, что рисует сцену. Иначе она
устареет при первой правке меша (что и есть смысл процедурности).

**Что уже есть и годится в основу:**

| Компонент | Что делает | Годится? |
|---|---|---|
| `IsoScreenshotTests.CreateIsoCamera` | Камера 3/4 справа-сверху (`IsoDir = (0.5, 0.5, −0.866)`), FOV 45°, дистанция от габарита так, что объект занимает ~70 % кадра | **Да, целиком.** 62 эталона `Iso*` доказывают, что ракурс читаем для всех типов. |
| `ElementFrameTests.CaptureFramePng` | `RenderTexture` → `Camera.Render` → `ReadPixels` → PNG; изоляция объекта через слой + `cullingMask` (`UI-GUIDELINES §9`) | **Да, с одной поправкой:** для плитки `ReadPixels`/PNG не нужны — `RenderTexture` отдаётся `RawImage` напрямую. |
| `ElementFactory.Create*` + `ElementSpawner` | Единственная фабрика; рождает элемент с декором по умолчанию | Да, но нужен флаг «песочница»: не регистрировать в `PartRegistry`, не поднимать `SceneRevision`, не попадать в `SceneAnalyzer` и в отпечаток `HierarchyPanelUI`. Сейчас такого флага нет — это основная работа. |
| `MaterialPreviewTests` / `DropdownHover` | Живой предпросмотр декора наведением на объекте сцены | Для миниатюр не нужен. Для палитры декоров хватает 2D-свотча: `MaterialDef.baseColor` + `texture` (лениво из `StreamingAssets/Textures`). |
| `ElementRenderers.BodyOf` | Полный набор рендереров составного элемента | Да — для перевода на изолированный слой. |

**Дизайн генератора** (`Rendering/ThumbnailRenderer`, ~200 строк + тест):

| Вопрос | Ответ |
|---|---|
| Что на картинке | Тип в **габаритах по умолчанию** и **декоре по умолчанию** из `SidebarCatalog.Item`. Иконка типа, а не портрет экземпляра. |
| Зависимые типы (фасад с 18 режимами двери, фитинг с проходом «с трассы») | Рендерить дефолт. |
| Когда генерировать | **Лениво, размазано по кадрам:** при первом показе группы — по 2 плитки на кадр. 24 плитки × (спавн ~1–3 мс + рендер 128² ~0,5 мс) ≈ 50–100 мс, размазанные по 12 кадрам — невидимо. |
| Размер | 128×128 для плитки 96 px (запас под HiDPI). Не 512, как в тестах. |
| Где хранить | Кэш `Application.persistentDataPath/thumbs/<kind>-<hash(dims, decor, BuildInfo.Version)>.png`; промах — рендер. Кэш нужен только чтобы не платить ~100 мс на запуске; в первой версии можно не делать. **В репозиторий PNG не класть** — протухнут при первой правке меша. |
| Тесты | `SidebarThumbnailTests` (PlayMode) — снапшоты всех плиток в `test-results/`, как `Iso*`. Плюс быстрый тест «каждый `SidebarItemKind` даёт непустую картинку» — ловит тип без рендереров на корне. |
| Стоимость | 2–3 дня: флаг песочницы в фабрике (полдня), рендерер (день), плитка в UI (полдня), тесты (день). Основная опасность — утечки: элемент песочницы обязан умирать сразу после рендера, иначе `PartRegistry` (коммит `6f41ad5a`) и отпечаток «Сцены» его увидят. |

### 2.4 Три варианта раскладки — пересчёт под 1366×768

**A. Левый док с плитками** (эволюция нынешнего). Ширина 260 px. Сверху поле поиска.
Группы — сворачиваемые заголовки, по умолчанию раскрыта **одна** (последняя
использованная). Внутри — сетка 2 колонки × плитки **96×96** (картинка 56 + подпись 2
строки; 104 на 768 px не проходит — см. ниже). Свёрнутый док — вертикальная **рейка иконок
категорий** 52 px, клик раскрывает док на этой группе. Пресеты — ряд иконок на плитке при
наведении или дропдаун под ней.

**B. Нижняя лента (Sims 2)** — см. 2.2.

**C. Палитра по вызову** (Blender `Shift+A`, Figma Assets). Постоянной панели нет; слева —
только рейка иконок 52 px. Клик по категории или клавиша открывает плавающее окно
`WindowChrome` 600×400 с поиском и сеткой 5×3 плиток; выбор закрывает окно и начинает
размещение.

| Критерий | A. Док с плитками | B. Нижняя лента | C. Палитра по вызову |
|---|---|---|---|
| Пиксели сцены (1366×768) | 1 106 × 674 (**81 %**) | 1 366 × 474 (**69 %**) | 1 314 × 674 (**96 %**) |
| Видно без прокрутки | 638 − поиск 32 − заголовок 34 = 572 px → **5 рядов × 2 = 10 плиток** при 96 px; при 104 px — 4 ряда = 8. Одна раскрытая группа (≤ 12 позиций) — почти целиком | 22 плитки | 15 на страницу окна + прокрутка колесом |
| 100+ типов | Поиск + свёрнутые группы | Страницы — плохо | Поиск первичен |
| Поиск | Поле сверху дока | Возможен, тесно | Курсор в поле сразу при открытии |
| Клавиатура | `/` фокус на поиск, стрелки по сетке, Enter — спавн | Неестественна | Лучшая |
| Ультраширокий | Нейтрально | Плохо | Нейтрально |
| Открываемость для новичка | Лучшая | Хорошая | Худшая — надо знать, что палитра существует |
| Совместимость с кодом | `SidebarUI` + `SidebarLayout` (быстрый путь, есть тесты) — раскладка меняется со «строки» на «сетку» | `SidebarLayout` переписать; конфликт со статус-баром | `WindowChrome` + `WindowBody` + `IProjectWindow` — всё есть |
| Цена | 3–4 дня + миниатюры | 5–6 дней + миниатюры | 3 дня + миниатюры |

**Что изменил пересчёт на 768 px.** Преимущество A «весь каталог на виду» на 1080p
(16 плиток) на 768 px сжимается до 10 плиток — одной группы. Разрыв между A и C по
«сколько видно» почти исчез, а по пикселям сцены C выигрывает 15 %. **Рекомендация
остаётся A, но с тремя обязательными поправками, которые сдвигают его к C:**

1. **По умолчанию док свёрнут в рейку иконок** (52 px), если высота экрана ≤ 800 —
   раскрывается кликом по категории, клавишей `/` или `Space`, и **сворачивается обратно
   после спавна** (как закрывается палитра в C). На 1080p и выше — раскрыт, как задумано.
   Отсюда D5 (иконки вместо букв) поднят в P1: рейка становится основным состоянием.
2. **Поиск — первый контрол**, курсор попадает в него при раскрытии клавишей.
3. **Плитка 96, не 104**, и одна раскрытая группа.

Причины не уходить в чистый C: он теряет новичка (нет постоянного намёка, что каталог
существует), а `SidebarUI`/`SidebarLayout` с их тестами переиспользуются без переписывания.
Ленту (B) не делать. Палитру (C) как второй вход можно добавить позже — данные и рендерер
плиток общие.

Порядок работ: (1) структура каталога 2.1 → (2) рейка иконок и авто-сворачивание (D5) →
(3) генератор миниатюр 2.3 → (4) сетка и поиск → (5) клавиатура. Пункт (1) обязан
опередить первый конструктивный элемент части 3.

### 3.3 Настройки, которые заказал пользователь, — и где они живут

Ответ на вопросы 1–6, 9, 10 один: **всё конфигурируемое — контролы в свойствах элемента
или в настройках; размеры пользователь меняет руками; валидация проверяет размеры
против настроек.** Это ровно механизм `PIP-02`: правило в `Pure/`, снимок сцены,
код в каталоге. Ниже — как ложится.

**Два уровня настроек.** Дефолты проекта — вкладка `SettingsConstructionTab` (ключи в
`SettingKeys`, паритет стережёт `McpSettingsParityTests`; хранятся в `KitchenSettingsData`).
Значения конкретного элемента — `[Undoable]`-свойства в его панели (`*FieldsEditor`),
инициализируются дефолтами при спавне. Так «все поля — в настройках» (ответы 9, 10) и
«отдельные настройки в свойствах» (ответы 1–6) — не противоречие, а два слоя одной
величины с одним писателем: панель.

#### Фундамент (ответы 1–4)

| Контрол | Где | Тип | Кто читает |
|---|---|---|---|
| Глубина промерзания | панель фундамента, **дропдаун** (значения 0,8 / 1,0 / 1,2 / 1,4 / 1,6 / 1,8 / 2,0 м или по городу — вопрос 18) | `[Undoable] FrostDepthMm` | `FND-01` |
| Тип грунта | панель, дропдаун {песок, супесь, суглинок, глина, торф, неизвестно = худший} | `[Undoable] SoilKind` | `FND-02`, коэффициент разрыхления в `FoundationQuantities` |
| Подушка: песок, щебень, трамбовка | панель, два поля мм + чекбокс | `[Undoable] SandMm, GravelMm, Compacted` | `FoundationQuantities` (коэффициент уплотнения), `FND-03` |
| Бетон: класс; арматура: Ø, шаг, защитный слой | панель, дропдаун {B15, B20, B25} + три поля | `[Undoable] ConcreteGrade, RebarDiameterMm, RebarStepMm, CoverMm` | `FoundationQuantities` (кг), `FND-04` |
| Ширина и глубина ленты | панель, **обычные размеры элемента** | `DimensionsMM` (уже есть у любого элемента) | все правила |

Правила (`Pure/Construction/FoundationRules`, dotnet-тесты, коды в `FoundationIssueCatalog`
и зеркалом в `SceneAnalyzer.IssueCatalog`, как `PIP-*`):

| Код | Правило | Уровень |
|---|---|---|
| `FND-01` | Глубина заложения ленты < глубины промерзания при пучинистом грунте (всё, кроме песка) | Ошибка |
| `FND-02` | Ширина подошвы < минимальной для типа грунта и толщины стены над ней (таблица — вопрос 22) | Ошибка |
| `FND-03` | Подушка тоньше минимума (песок < 100 мм или щебень < 100 мм при заданной трамбовке) | Предупреждение |
| `FND-04` | Защитный слой < 2Ø или шаг арматуры > ширины ленты | Предупреждение |
| `FND-05` | Под несущей стеной нет ленты (осевая стены не покрыта фундаментом) | Ошибка — это уже геометрия, `WallCentreline` × полилиния ленты |

Что важно: **правила не меняют размеры.** Пользователь ввёл 800 мм глубины при промерзании
1 400 — получает `FND-01` в окне «Ошибки» и красную подсветку, как у любого нарушения.
Никакого автоисправления, никаких «рекомендованных» значений в поле (§9: вычисляемое —
строкой только для чтения; можно показать «Минимум по промерзанию: 1 400 мм» серой строкой).

Константы (минимальные ширины, массы арматуры, коэффициенты разрыхления) — в таблицах
данных `Pure/Construction/*Tables.cs`, не в литералах, и каждая с источником в тесте.

#### Стены (ответы 5, 6)

| Контрол | Где | Тип |
|---|---|---|
| Технология | панель стены, дропдаун {кирпич 250×120×65, кирпич 250×120×88, газоблок 600×300×200, брус (сечение), каркас (шаг стоек)} | `[Undoable] Masonry` (id из таблицы `MasonryUnit`) |
| Толщина шва, мм | панель стены | `[Undoable] JointMm` |
| Запас, % | панель стены | `[Undoable] WastePercent` |

Дефолты трёх полей — в `SettingsConstructionTab`. Правило одно и дешёвое: `WAL-01` —
толщина стены не кратна формату кладки с учётом шва (250 / 380 / 510 для кирпича 250×120 со
швом 10) — предупреждение, не ошибка: стена такой толщины строится, но с подрезкой.

#### Кровля и забор (ответы 9, 10): «пользователь ставит — система считает сама»

Что значит «считает сама» — что выводится из геометрии, а что спрашивается один раз:

| | Выводится из сцены | Спрашивается один раз (дефолт в настройках, поле в панели) |
|---|---|---|
| **Кровля** | Контур — внешний контур стен верхнего уровня (`WallCentreline` + толщины) или полигон пола уровня; для двускатной — конёк вдоль длинной стороны (кнопка «повернуть» на 90°); площадь скатов, длина конька, карнизов, водостока, число стропил, объём бруса стропил | Тип {одно-, двускатная, вальмовая}, уклон (°, `0,0`), свес (мм), шаг стропил, сечение стропила, покрытие {металлочерепица м², шифер лист шт, …}, запас % |
| **Забор** | Полилиния — пользователь тянет точками (как полигон пола) или «по границе участка»; число столбов = Σ по прямым ⌈L/шаг⌉ + 1, пролёты (м), бетон (м³), листов/штакетин (шт), лаг (м.п.) | Тип {профлист, штакетник, сетка}, высота, шаг столбов, сечение столба, диаметр и глубина ямы, число лаг |

«Один раз» — потому что эти величины **не выводятся**: уклон и свес — решение, а не
следствие; тип столба — покупка, а не геометрия. После первого ввода они живут в
`SettingsConstructionTab` и каждая следующая крыша/забор берёт их без вопросов.

### 3.4 Этажность: отдельный интерфейс переключения

### 3.5 Вентиляция на слое портов санузла — что обобщается, что параметризовать, какой ценой

Ответ 7: «вентиляцию делать тем же механизмом, что трубопровод санузла: выделить общую
логику и переиспользовать». Разбор по слоям, снизу вверх.

#### Что уже общее и переиспользуется как есть (цена 0)

| Компонент | Почему не про трубы |
|---|---|
| `SnapPort { Position, Outward }` (`Geometry/`) | Точка + нормаль. Ни радиуса, ни сечения. |
| `ISnapPorts` (`SnapPortCount`, `SnapPortAt`) | Любой элемент, объявивший устья, садится «устье в устье» через `SnapCore.TrySnap` → `SnapPortSeat` — до граневых детентов. Воздуховод получает посадку бесплатно. |
| `SnapPortSeat`, `SnapNeighbourFacts`, `SnapPortDock` | Ранг встречности и сдвиг — геометрия, не сантехника. |
| `PortTurn` (`TurnOnto`, `Rotate90`, `RotateWithTwist`) | Доворот устья в устье. Единственная оговорка — см. «твист» ниже. |
| `PipeNetwork.Build(ports)` | Паросочетание портов по `Connects` + список свободных — граф, не труба. |
| `PipeJoint.Connects` (расстояние ≤ `Tolerance.ContactMm`, оси противоположны) | Правило стыка — общее. |
| `PipeRules` / `PIP-01` (открытый конец), `PIP-03` (пересёк препятствие) | Открытый конец воздуховода — та же ошибка; пересечение — та же. |
| `PipeFittingSeatChoice` («максимум связей» при постановке фитинга) | Перебор портов × 4 твиста — общий. |
| `PipeFittingSizeLink` (диаметры **выводятся** с трассы, единственный писатель) | Правило «фитинг не имеет своего размера — берёт с соседа» одинаково нужно воздуховодам: отвод Ø160 на трассе Ø160. |
| `IMountsOnTarget`, `PipeDocking.ReseatAfterRotation` | Крепление и пересадка при повороте кнопками. |

#### Что прошито сантехникой и требует параметризации

| Что | Как прошито | Что сделать | Цена |
|---|---|---|---|
| `PipePort.OwnerKind : PipeNodeKind` и `SizeId : string` по `PipeSpec` (ГОСТ 3262-75) | Порт знает, что он трубный | Вынести в `Pure/Ports/`: `Port { ElementId, PortIndex, PositionMm, OutwardAxis, ProfileId }` и `PortNetwork`, `PortJoint`, `PointMm`, `PipeAxis` → `Axis`. `PipePort` становится тонкой обёрткой (или псевдонимом) — тесты `PipeNetworkTests`, `PipeJointTests` переезжают без изменения утверждений | 1–2 дня, чистый рефакторинг переименования, dotnet-тесты зелёные до и после |

#### Что не обобщается и не надо пытаться

- **Вентзазор в стене — не воздуховод.** Это слой толщиной 30–50 мм между утеплителем и

- **Уклон трубы** (если появится для канализации) воздуховоду не нужен; **сечение по
  расходу** (м³/ч → Ø) — расчёт, а не геометрия; не делать, пока не попросят.

2. Круглый воздуховод + отвод + тройник + заглушка + решётка на `LegFrame` — **3–4 дня**;
   это уже рабочая вентиляция для типового дома.
3. Прямоугольный профиль, скошенный отвод, переход круг↔прямоугольник, проверка твиста —
   **4–5 дней**.
4. Правила `VNT-*`, UI, сайдбар (одной плиткой), спецификация — **2–3 дня**.

Всего ~2 недели; половина цены — прямоугольное сечение. Если в первом доме только круглые
каналы — пункт 3 откладывается без потерь.

### 3.6 Как подсчёт объёмов вырастает из спецификации, а не строится рядом

Сейчас `SpecificationManager.Build` делает три вещи: собирает строки с элементов,
группирует одинаковые, суммирует. Все три остаются. Меняется **что такое строка**:

```
сегодня:  SpecLine { name, dimsMM, count, areaPerBoardM2, totalAreaM2, material, grooves, edges }
станет:   SpecLine { section, name, material, unit, qtyPerItem, count, qtyTotal, dimsMM?, grooves?, edges? }
```

- Деталь ЛДСП: `section=Мебель, unit=м², qtyPerItem = w·h` (уже `BoardFaceArea`), плюс
  строка `unit=м` для кромки.
- Стена: `Wall.Quantities()` — по строке на материал: «Кирпич 250×120×65 — шт — 1 240»,
  «Раствор — м³ — 0,31». Слои — каждый элемент сам: «Минвата 100 — м² — 18,4».
- Фундамент: «Выемка грунта — м³», «Песок — м³», «Щебень — м³», «Бетон B20 — м³»,
  «Арматура Ø12 — кг», «Опалубка — м²».
- Кровля: «Металлочерепица — м²», «Стропило 50×150 — шт + м³», «Конёк — м».
- Воздуховод: «Воздуховод Ø160 — м», «Оцинковка — м²», «Отвод Ø160 90° — шт».

Правило одно: **элемент знает свои количества, спецификация знает только как складывать.**
Это уже так для `ISpecificationParts`; `IQuantifies` — его обобщение. Жёсткое исключение
`Wall`/`BasePlate` (D12) заменяется на «элемент без `IQuantifies` не попадает».

Формулы — только в `Pure/Construction/` (dotnet-тесты, Stryker), константы — в таблицах
данных. CSV получает `Section;Unit;Qty` и остаётся обратно совместимым по первым столбцам.
Денег в строке нет (ответ 13), документа нет (ответ 14).

список материалов (бетон + арматура против брус + доска + утеплитель между лагами). **Не
зависят:** сущность «перекрытие принадлежит уровню и лежит на его отметке», связь «стена
верхнего этажа опирается на перекрытие» (валидация опоры), секция «Перекрытия» в
спецификации и плитка в каталоге. Это общий день из 2–3; его можно сделать вместе с
уровнями (п. 3) как `SlabElement` с толщиной и `IQuantifies` = «бетон м³» — а ветвь «лаги»
добавить как второй тип того же элемента, когда придёт ответ. Риск переделки: нулевой для
плиты, один день для лаг.

Что переделать **заранее**, иначе придётся переделывать дважды:

1. `SpecLine` с единицей (п. 1) — до первого конструктивного элемента.
2. Каталог как данные (п. 2) — до первой новой группы.
3. «Пол = 0» → отметка уровня (п. 3) — до фундамента и перекрытий.
4. Вынос `Pure/Ports/` (3.5, шаг 1) — до первого класса воздуховода; иначе воздуховод
   унаследует `PipeNodeKind`, и разделять придётся с двумя потребителями.
