# Как выкладывать релиз десктопа (процедура для агента)

Триггер: пользователь просит «выложить/опубликовать релиз / инсталлятор / сборку».
Тогда агент ОБЯЗАН оформить «Что нового» сам и опубликовать через скрипты ниже —
не выкладывать релиз со случайным или авто-сгенерированным описанием.

## Инструменты (в `installer/`)
- `commits-since-release.ps1` — печатает коммиты с прошлого релиза (только git log/show,
  ничего не меняет) + подсказку-«области» по путям.
- `make-release-notes.ps1` — подставляет готовый Russian-чанджлог в **единый шаблон**
  (`Что нового` / `Установка` / `SmartScreen` / `Лицензия`) и пишет markdown в UTF-8.
- `publish-github.cmd -NotesFile <файл>` — тегирует, пушает тег, делает/догружает релиз,
  вызывает `make-release-notes.ps1`, печатает ссылку `…/releases/latest/download/…`.

Шаблон и неизменные разделы живут в `make-release-notes.ps1` — править оформление надо там.
Агент пишет **только** блок «Что нового».

## Что скрипты теперь не дают сделать молча
- **Версия берётся из `BuildInfo`** (то, что вшито в собранный плеер), а не из
  `output\version.txt`. Если `version.txt` отстал — публикация падает с требованием
  пересобрать установщик. Раньше побеждал `version.txt`, и `-NoBuild` после нового билда
  догружал СТАРЫЙ setup в УЖЕ выпущенный релиз.
- **`-NotesFile` с несуществующим путём — ошибка**, а не заглушка «Список изменений не заполнен».
- **Повторный запуск по существующему тегу обновляет и тело релиза** (`gh release edit`), а не
  только ассет.
- **`-DryRun` печатает готовое тело релиза** целиком.
- **`-PreRelease`** помечает выпуск предварительным. Учитывать: GitHub исключает prerelease из
  `/releases/latest`, поэтому ссылка `releases/latest/download/…` на него НЕ работает и
  **автообновление внутри приложения такой выпуск не увидит**. Промежуточные сборки, которые
  должны доехать до пользователя обновлением, публикуются обычным релизом.
- Установщик в релизе обязан называться `KitchenDesigner-Setup-<тег без v>-x64.exe`: апдейтер
  отказывается ставить ассет от другой версии (иначе — тихий откат назад и вечное «доступно
  обновление»).

## Загрузка релиза: черновик, проверка, публикация (`publish-release.ps1`)
`publish-github.cmd` не делает `gh release create <тег> <setup>` одним вызовом: тот создавал
релиз, лил 60 МБ и публиковал в одном шаге, и при обрыве по тайм-ауту оставлял ПУСТОЙ черновик.
Теперь шаг [4/5] идёт так: релиз создаётся ЧЕРНОВИКОМ без ассета → ассет грузится с повторами
(3 попытки, тайм-аут попытки = max(180 с, 60 с + 10 с на МБ), повисший `gh` снимается вместе с
дочерними процессами; `--clobber` стирает недогруженный остаток) → на стороне GitHub проверяется,
что ассет есть, `state=uploaded` и размер равен локальному → только после этого черновик снимается
(`--latest`, для `-PreRelease` без него). Любой провал печатает блок «СОСТОЯНИЕ НА GITHUB» (черновик
ли, какой ассет) и выходит с кодом 1; **повторный запуск той же команды дожимает начатое** — каждый
шаг идемпотентен, тег и сборка заново не нужны (`-NoBuild`, готовый setup).

Весь конвейер (сборка, два дымовых прогона, загрузка) длиннее 10 минут: запускать его фоновой
задачей, а не под лимитом в 10 минут на вызов — иначе убитый вызов оставит черновик (теперь он
дожимается повторным запуском, но терять время незачем). Пробный прогон без публикации:
`powershell -File installer\publish-release.ps1 -Tag … -NoPublish -DryRun` (параметры — в шапке
скрипта).

## Шаги
1. Убедиться, что публикуемый код собран и тесты зелёные (`build.cmd`, на своё усмотрение
   `build.cmd -RunTests`). Версия = `BuildInfo.Version` (`installer\get-version.ps1`).
2. Собрать установщик, если его нет: `installer\build-installer.cmd -NoBuild`
   (или без `-NoBuild` — сначала пересоберёт плеер). Итог:
   `installer\output\KitchenDesigner-Setup-<вер>-x64.exe`, версия — в `output\version.txt`.
3. Взять историю:
   `powershell -File installer\commits-since-release.ps1 -TargetTag v<вер>`
   (база = последний тег до публикуемого; при `-TargetTag` он исключается).
4. Оформить чанджлог (см. правила ниже) и записать краткий список на русском в
   временный файл, например `%TEMP%\changelog-<вер>.md` (строки `- …`).
5. Опубликовать: `installer\publish-github.cmd -NoBuild -NotesFile <файл>`.
   Перед этим можно проверить тело без публикации: тот же вызов с `-DryRun`, либо
   напрямую `make-release-notes.ps1 -ChangelogFile <файл> -OutFile …` и прочитать.
6. Проверить: `gh release view v<вер>` и что `api …/releases/latest` отдаёт нужную версию/ассет.
7. Дымовая проверка СОБРАННОГО плеера теперь автоматическая и встроена в шаг публикации:
   `publish-github.cmd` сам запускает `tools\smoke-test.ps1` на `Build\KitchenDesigner.exe`
   (на своём MCP-порту, не 9337 — не мешает уже запущенному приложению пользователя) сразу
   после сборки инсталлятора и ДО тега/релиза. Она проверяет то, что не видно ни одному
   тесту, который гоняет редактор: приложение запускается, MCP отвечает
   (`initialize` → `serverInfo.name=unity-kitchen`), сквозной путь создание/чтение/удаление
   элемента через MCP и корректное завершение процесса без осиротевшего процесса.
   Провал — публикация останавливается, ничего не тегируется и не грузится на GitHub.
   Раньше это был ручной шаг (curl вручную) — не делай его руками, скрипт делает то же
   самое и больше.

   Сохранение и загрузка проекта проверяются там же: `save_project` пишет ТОЛЬКО в
   каталог, переданный плееру аргументом `-mcpSaveDir`, и без этого аргумента отказывает
   — поэтому дымовой прогон поднимает плеер со своей временной папкой и не может
   дотянуться до живого проекта пользователя. Путь сравнивается по реальному
   нормализованному имени, так что `..`, регистр и символические ссылки за пределы
   каталога не выводят.

   Превышение порога времени шага печатается заметно, но публикацию НЕ останавливает:
   релиз обязан вставать на неверном результате, а не на медленном ответе. Числа и
   что делать при превышении — `agents/TESTS.md`, раздел про дымовую проверку.

8. **Дымовая проверка ОБНОВЛЕНИЯ установщиком** — тоже автоматическая, сразу после шага 7 и
   тоже до тега: `tools\installer-smoke.ps1 -SetupPath <setup>`. Плеер может быть исправен, а
   установщик — не уметь его обновить: v0.1906…v0.2037 выходили с тихим обновлением, которое
   откатывалось. Приложение запускает setup и только потом закрывается; Unity-плеер
   выходит секунды, Restart Manager закрыть его не может («Some applications could not be shut
   down»), под `/SUPPRESSMSGBOXES` ответ по умолчанию — Abort, и setup пишет «Rolling back
   changes». Пользователь видел «откат», потом закрывались оба окна.

   Скрипт ставит собранный setup **в песочницу** `%TEMP%\kd-smoke-<guid>\app` три раза, каждый с
   `/LOG` в `test-results\installer-smoke\`: обычной тихой установкой и «гонкой обновления» —
   приложение песочницы запущено, setup стартует с ключами самого апдейтера (берутся из
   `InstallerCommandLine.cs`) и только через 4 с приложение получает WM_CLOSE. Провал — строка
   «Rolling back changes», код выхода ≠ 0, нет «Installation process succeeded» или после
   установки не поднялось приложение (`/RELAUNCH`). Третий проход — «отмена»: приложение так и не
   закрывают; через `RelaunchAskAfterSec` setup обязан спросить «Закройте Kitchen Designer и
   нажмите ОК», на ОК при всё ещё запущенном приложении — спросить снова, на Отмена — выйти,
   ничего не поставив и не откатывая (файлы песочницы и запущенное приложение не тронуты). В конце
   песочницу снимает её собственный деинсталлятор, временный каталог удаляется.

   **Установка пользователя не трогается, открытое у него приложение не мешает.** Песочница — это
   тот же setup с ключами `/SMOKE=1 /DIR= /MUTEX= /APPARGS=` (обрабатывает `[Code]` в
   `KitchenDesigner.iss`; без `/SMOKE` они игнорируются и поведение для людей прежнее, а `/SMOKE`
   без `/DIR` и без своего `/MUTEX` setup отказывается стартовать). В песочнице не пишутся запись
   «Программы и компоненты» (`CreateUninstallRegKey=NotSmoke`: AppId тот же, что у настоящей
   установки), ярлыки меню «Пуск» и рабочего стола, ассоциация `.kdproj`; `InstallLanguage` уходит
   в `HKCU\Software\KitchenDesigner-Smoke` — контракт «первая установка пишет, тихое обновление не
   перезаписывает» проверяется на этой копии ключа. Мьютекс: setup ждёт `/MUTEX=<имя этого
   прогона>`, а приложение песочницы запускается с `-mutex <имя>` (и `/RELAUNCH` поднимает его с
   теми же ключами через `/APPARGS=`), поэтому они видят только друг друга, а не приложение
   пользователя; у людей приложение держит прежнее общее имя и обновление идёт как раньше. До и
   после скрипт снимает отпечаток всего, что принадлежит пользователю (файлы установки по SHA-256,
   запись в «Программах и компонентах», ассоциация `.kdproj`, `HKCU\Software\KitchenDesigner`,
   папка меню «Пуск», ярлык на рабочем столе), и падает при расхождении хоть на байт. Приложение
   пользователя можно не закрывать. Не покрыто: обновление поверх файлов именно ПРОШЛОЙ версии
   настоящей установки — песочница начинается с пустого каталога, а «обновление» идёт поверх её
   собственной первой установки.

   Пока setup ждёт выхода старой копии, он показывает «Ожидаем закрытия приложения…»; срока
   у ожидания нет — только вопрос и Отмена.

   Ручной запуск: `powershell -File tools\installer-smoke.ps1` (setup по `output\version.txt`).
   Упала «гонка» — читать в её логе строки перед «Rolling back changes» и строки
   `Update:` (сколько setup ждал выхода старой копии). Вопрос о даунгрейде в `.iss` — обычный
   `MsgBox`, который тихий прогон не отвечает; песочница его пропускает (версию настоящей установки
   она не читает).

## Правила отбора изменений для «Что нового»
- **Только DESKTOP Unity.** В релиз попадают изменения, относящиеся к собранному
  Windows-приложению: правки в `Assets/Scripts/**`, `Assets/Editor/**`, `Assets/Scenes/**`,
  `Assets/StreamingAssets`, материалах/текстурах, UI, и пр., что пользователь видит в десктопе.
- **Игнорировать** изменения, которые пользователь десктопа не заметит: коммиты только про
  тесты (`Assets/Tests/**`), внутреннюю инфраструктуру (`docs/**`, `Packages/*`, CI,
  скрипты сборки) — их в перечень НЕ вносить.
- **Фиксы не перечислять отдельно.** Если в этот релиз вошла фича и несколько `fix:`/
  `refactor:` к ней — дать ОДНУ строку «Добавлено: …», поглотив её исправления. Отдельные
  багфиксы показывать лишь когда это самостоятельное исправление пользователя
  (например: «Исправлено: …»).
- **Кратко и по-русски.** 1 строка = 1 пункт, без хэшей и имён файлов. Если из сообщения
  коммита непонятно, что за фича — только тогда глянуть diff этого коммита.
- Первый релиз без прошлого тега: описать ключевые возможности в 3–6 пунктах.

## Пример блока «Что нового» (то, что кладёт агент в -NotesFile)
```
- Приложение теперь само проверяет обновления на GitHub при запуске и предлагает
  обновиться в один клик (Windows).
- Добавлена привязка досок к родительской доске/фасаду.
- Исправлено: валидация пассажирского фасада следует за ним при перетаскивании.
```

## Язык установщика и язык приложения
- В `[Languages]` десять языков (по числу `Assets/StreamingAssets/Localization/*.json`; сверяет
  `InstallerScriptGuardTests`). Диалог выбора — `ShowLanguageDialog=auto`: показывается, только
  если язык Windows не подошёл ни к одному. Новый язык приложения = новая строка в `[Languages]`
  + `<имя>.AppLanguageCode=<код файла>` и переводы `[CustomMessages]`.
- Бандл Inno переводов на упрощённый китайский не имеет: `installer\Languages\ChineseSimplified.isl`
  даёт только имя и LCID, тексты мастера английские.
- Контракт с приложением: setup пишет обычную строку `HKCU\Software\KitchenDesigner\InstallLanguage`
  (REG_SZ, код языка приложения). Приложение читает её при старте ТОЛЬКО если в PlayerPrefs ещё нет
  «Language» и переносит в PlayerPrefs (`LanguageChoice.InstallerLanguageToKeep`). Тихое
  автообновление существующее значение не перезаписывает. Приоритет: выбор в приложении >
  установщик > язык ОС > en. `tools\installer-smoke.ps1` проверяет значение и что обновление его не трогает (на песочничной
  копии ключа, не на ключе пользователя).
